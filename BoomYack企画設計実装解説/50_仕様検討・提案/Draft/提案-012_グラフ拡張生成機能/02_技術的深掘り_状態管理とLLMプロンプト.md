# 提案-012: 技術的深掘り — 状態管理とLLMプロンプト設計

## 1. 仮配置状態 (Draft State) のライフサイクル管理

AIが生成したノード群を「確定」させるまでの間、システムの整合性を保つための設計。

### 1-1. データ構造への影響
- **`GraphNode` モデルの拡張**:
  ```typescript
  interface GraphNode {
    id: NodeId;
    text: string;
    state: 'normal' | 'draft'; // 'draft' 状態を追加
    metadata: {
      isTemporary: boolean;
      generatedBy: 'AI-Expand-v1';
    };
  }
  ```
- **一時的なIDの扱い**: AI生成時にサーバー側で `tmp_` プレフィックス付きのIDを発行。採用（Accept）時に正規のUUIDに振り直す、またはそのまま採用する。

### 1-2. 保存（永続化）戦略
- **原則**: `state: 'draft'` のノードは、ブラウザを閉じると消失するか、ファイル保存時に明示的に除外される。
- **理由**: 「書きかけのAI提案」がプロジェクトの正式なデータセットを汚染することを防ぐ。
- **例外**: 大規模な生成（50ノード以上など）の場合は、セッション情報として別途キャッシュに保持することを検討。

## 2. LLM プロンプト構築（コンテキスト抽出アルゴリズム）

AIに「気の利いた続き」を書かせるためのコンテキスト構築。

### 2-1. 抽出範囲 (Extraction Scope)
起点となるノード `N` に対し、以下の情報を収集する：
1. **直接の親 (Primary Parent)**: `N` が属する文脈の上位概念。
2. **兄弟ノード (Siblings)**: すでに展開済みの他案。AIの重複を防ぐ。
3. **グラフのグローバルルール**: 「語尾は〜です」「専門用語はこれを優先」等のグローバル設定。

### 2-2. プロンプトテンプレート案
```text
システム: あなたはグラフ構造の思考整理を助けるエージェントです。
コンテキスト:
  階層: [Root] > [Parent] > [Current Node: {N.text}]
  既存の他案: {Siblings.map(s => s.text).join(', ')}
依頼: {N.text} について、さらに具体化・深掘りする後続ノードを3〜5個提案してください。
制約: 出力は以下のJSON形式厳守。
{
  "nodes": [{"text": "...", "reason": "..."}],
  "edges": [{"from": "{N.id}", "to": "new_id"}]
}
```

## 3. 並行操作の調停 (Concurrency Management)

AI生成中にユーザーが手動でグラフを操作した場合の挙動。

- **ロック戦略**: 生成中は起点ノード `N` の編集をロックする（UI上で `readonly`）。
- **破棄条件**: 起点ノード `N` 自体が削除された場合、進行中のAI生成リクエストは中断、または生成結果を破棄する。
- **Undo/Redo**: 「Accept」一回につき、Undoスタックに1つエントリを積む。一括操作を可能に。

## 4. 自動レイアウトとの連携

AIは「論理的な繋がり」は生成できるが「視覚的な座標」は生成できない。

- **プロトタイプ解**: 起点ノードの右側に、縦に等間隔で並べる。
- **本採用案**: 提案-015「自動レイアウト・座標計算」に座標決定を委ね、論理的な接続情報のみを生成結果として受け取る。
