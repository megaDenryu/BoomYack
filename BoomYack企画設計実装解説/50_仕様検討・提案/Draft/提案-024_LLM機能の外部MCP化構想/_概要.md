# 提案-024: LLM機能の外部MCP化構想

## 1. 概要
アプリケーション内部にLLMの呼び出しAPI（Gemini等の直接実行）を抱えるのではなく、Model Context Protocol (MCP) のサーバーとして機能を提供し、既存の有料AIエージェントクライアントに委譲する構想の提案です。

## 2. 現状と課題（As-Is）
- 現在はBoomYackの内部でLLMサービス（Gemini 2.0 Flash）を利用してノード分解などを行っている。
- しかし、LLMのAPIキーの管理や、より高度な推論、または最新のエージェント基盤のベストプラクティスを自前で維持していくのは開発・運用コストがかかる。
- LLMのAPIがないと自立型エージェントやRAGなどの高度な機能は成り立たないが、自前で持つよりも既存の「有料のエージェント環境」と連携させた方が質の高いエコシステムを構築できる可能性が高い。

## 3. 提案（To-Be）
- **MCPサーバーとしてのBoomYack機能提供**:
  - BoomYackの「グラフ操作」「キャンバスの読み取り」「ノードの更新」などの機能をMCPのツールとして定義し、外部のAIエージェント（Cursor, ClineなどMCP対応のモデル）に提供する。
- **アーキテクチャのシフト**:
  - インハウスのLLM実行から、外部知能へのインターフェース開放へのシフト。
  - AI側の高度なコンテキスト管理は外部クライアントに任せ、BoomYack側は「操作可能なキャンバスのAPI」として振る舞う。

## 4. 影響範囲
- アプリケーション全体の外部アクセスインターフェース（MCPサーバーの立ち上げ）
- LLMドメイン（`api/LLM/`）の役割変更

## 5. 次のステップ
- MCP仕様の調査と、BoomYackをMCPサーバーとして起動するためのPython実装のモックアップ作成。
- 外部エージェントからの接続テスト。
