# 設計2026-07-16: 付箋の表示・操作仕様復元

## 0. この文書の目的

付箋の見た目と操作は、TypeScriptの明示的なモデルだけでは決まっていない。CSSの
`content-box`、透明なpadding、`transform`が作る包含ブロック、絶対配置、DOM接続後の
非同期高さ計測が組み合わさって成立している。そのためDOMやCSSを局所的に整理すると、
コードから読み取れなかった前提が壊れる。

本文書は、正常動作の基準としてユーザーが指定したBoomYackコミット
`00fe0b0bda1c55c5827d5fdad44361d0fadd46cb`と、同時点のSengenUIコミット
`500442957ab870b3f200f97aa1d97c7645a0723d`から、付箋の表示・操作仕様を復元する。

後続コミット`8113de5`の新クラス`付箋枠`は壊れているため、仕様の根拠には用いない。

## 1. 復元の原則

正常コミットで利用者から見える付箋の外観は、すべて意図された仕様として保存する。
「CSSの副作用でたまたまそう見えるもの」はない。現在そう見えるようにするため、現在のCSSと
DOM構造が選ばれている。ただし、付箋をどう生成するか等の製品操作仕様まで無条件に正しいとは
みなさない。

一方、その結果を作る具体的な技法は置き換えてよい。たとえばcontent-boxグラデーション、
透明padding、fixed要素の包含ブロック、非同期の高さ通知は実現機構であり、より明示的で安全な
CSS・DOM・TypeScriptへ変更できる。ただし変更前後の見た目と操作感は一致させる。

本文書では次の4種類を区別する。

- **確定仕様**: ユーザーが意図を明言した外観・操作結果
- **復元仕様**: 正常コミットの外観・操作結果としてコードから復元した保存対象
- **再設計対象**: 現在の製品操作として存在するが、仕様自体に問題があり得るため維持を前提にしない
- **コード上の疑義**: 静的解析では複数の結果が考えられ、実際に画面へ現れる結果を実測する必要がある箇所

コード上の疑義も、実測された現在の外観を正とする。製品操作は、現状を記録したうえで仕様を
維持するか再設計するかを別に判断する。

### 1.1 問題の因果関係

現在の問題は、CSSだけを単独の原因と捉えると不正確になる。

```text
問題を含む、または意味を表せていない製品操作仕様
→ 実際の付箋と操作UIを同じDOM・同じクラスで表現
→ 見た目と操作範囲を両立するためDOM構造が歪む
→ 歪んだ構造を補償する特殊なCSS技法が必要になる
→ CSS寸法とTypeScript寸法を同期する実行順序への依存が生まれる
→ 一部をリファクタすると、別の補償関係が壊れる
```

したがって、目標は特殊なCSSだけを通常のCSSへ書き換えることではない。先に製品操作、意味上の
部品、DOM、CSS、初期化順序の順に責務を引き直す必要がある。

## 2. 付箋を構成する矩形

付箋には少なくとも2つの異なる矩形がある。

### 2.1 付箋本体矩形

`position`を左上、`size`を幅と高さとする矩形。利用者が黄色い付箋そのものとして認識する
領域であり、シリアライズされる位置とサイズもこの矩形を表す。

- 新規の自由テキスト付箋は幅200px、高さ52px
- 52pxは上下padding 16pxずつと1行高20pxの合計
- 背景色、テキスト、フォーカス時の青いtextarea輪郭はこの矩形内に収まる

これは**確定仕様**である。

### 2.2 操作領域矩形

本体矩形を上下左右へ30pxずつ拡張した透明な矩形。

```text
操作領域の位置 = position - (30px, 30px)
操作領域のサイズ = size + (60px, 60px)
```

正常コミットでは`付箋ホバー領域`がこの矩形を表す。ドラッグ、選択、ホバー、左右の
リサイズハンドル、衝突判定の基準になる。

これは**復元仕様**である。ただし30pxという値を将来も固定するかは別途判断できる。

### 2.3 選択枠が囲む矩形

選択枠は本体矩形ではなく、リサイズハンドルを含む操作領域矩形を囲む。

- 選択: 2pxの赤い破線
- ホバー: 2pxの緑の破線
- 矢印接続点の一括表示対象: 2pxの薄緑の破線
- 通常: 枠なし
- `outline`なのでレイアウト寸法には加算しない

これはユーザーが「緑の枠矩形はハンドルを包む」と明言した**確定仕様**である。

### 2.4 衝突判定矩形

衝突判定には本体矩形ではなく操作領域矩形を使う。設定パネル等の重なり回避は、黄色面だけ
ではなく周辺操作領域との重なりも避ける。

これは`get衝突判定用矩形()`と衝突判定サービスから復元した**復元仕様**である。

## 3. 正常コミットのDOMとCSSが担っている意味

正常コミットの概念上のDOMは次の構造である。

```text
付箋ホバー領域（操作領域、位置を持つルート）
├─ 付箋コンテンツコンテナ（通常フローでcontent boxに配置）
│  └─ I付箋コンテンツView
├─ 左リサイズハンドル（絶対配置）
├─ 右リサイズハンドル（絶対配置）
└─ 矢印接続可能なもの（絶対配置）
   ├─ 上接続点
   ├─ 右接続点
   ├─ 下接続点
   └─ 左接続点
```

### 3.1 黄色面は実要素ではない

`付箋ホバー領域`自身の寸法は操作領域矩形である。同じ要素へ30pxのpaddingと
`box-sizing: border-box`を設定し、背景を
`linear-gradient(色, 色) content-box`として、中央のcontent boxだけを塗っている。

この結果、DOM上は大きな透明要素だが、中央だけが本体矩形と同じ寸法で黄色く見える。
textareaは透明なので、黄色面は外側要素の背景が透けて見えている。

これは正常コミットを説明する**実現機構**である。新実装でグラデーション自体を維持する必要は
ないが、「本体矩形だけに背景色が表示され、周囲30pxは透明」という見た目は必ず維持する。

### 3.2 コンテンツは通常フローでcontent boxへ入る

正常コミットではコンテンツを絶対配置していない。操作領域ルートの通常フローへ置くことで、
paddingの内側、すなわち黄色く塗られたcontent boxへ自然に収まる。

新しい本体要素を導入する場合も、本体の左上が必ず
`操作領域の左上 + (30px, 30px)`になる必要がある。単に`position: absolute; top: 0; left: 0`
とすると、paddingによる配置規則を失う可能性がある。

### 3.3 リサイズハンドルは黄色面の端ではなく操作領域の端にある

左右ハンドルは幅10px、`top: 0; bottom: 0`で操作領域の全高に伸びる。通常は透明で、
ホバー中だけ半透明の青になる。左は`w-resize`、右は`e-resize`カーソルを示す。

したがって、黄色面とハンドルの間には透明な操作余白がある。選択枠がハンドルを囲むという
仕様とも一致する。これは**復元仕様**である。

## 4. サイズ変更の仕様

### 4.1 高さはコンテンツが決め、枠へ一方向通知する

枠が利用可能な幅を与え、コンテンツが自然高さを`onHeightChange`で枠へ通知する。枠は通知を
受けて本体高さ、操作領域高さ、接続点座標、接続済み矢印を更新する。

これは`I付箋コンテンツView`に明記されている**確定仕様**である。

### 4.2 自由テキストの空文字

空文字ではplaceholderの折り返しや`scrollHeight`を高さの根拠にしない。

- textareaの`height`を既知の`minHeight`へ明示的に固定する
- 枠へ通知する高さにもDOM実測値ではなく同じ`minHeight`を使う
- document未接続時の`offsetHeight`を使わない

これにより空の1行付箋は52pxになり、textareaの青いフォーカス輪郭も黄色面からはみ出さない。
これは`00fe0b0`で修正され、ユーザー確認済みの**確定仕様**である。

### 4.3 自由テキストの非空文字

非空文字では一度`height: auto`にしてから`scrollHeight`を読み、内容に合わせて伸縮する。
`overflow: hidden`かつ手動リサイズ無効なので、通常はtextarea内スクロールではなく付箋自体の
高さ変更として表現する。

### 4.4 初期化順序

textareaは構築直後ではなく`setTimeout(..., 0)`で高さを通知する。これは親の初期化とDOM接続を
待つためである。外部から`setValue()`した場合も同様に遅延して再計算する。

DOM実測が必要な非空文字では必要な待機だが、空文字は既知の最小高さを同期的にも決定できる。
新実装では「遅延通知が来ないと別部品の座標まで壊れる」構造を作ってはならない。

### 4.5 横リサイズ

- 左ハンドル: 左端を移動し、右端を維持する。幅を`-deltaX`、位置を`+deltaX`する
- 右ハンドル: 左端を維持し、幅を`+deltaX`する
- 画面上のポインター差分はキャンバス拡縮率で割って描画座標差分へ変換する
- リサイズのたびに接続点と接続済み矢印を更新する

これは**復元仕様**である。

正常コミットには最小幅の制約がなく、幅0以下も型上は生成可能である。ただし通常操作で実際に
どこまで縮められ、画面上でどう見えるかは静的解析だけで確定しないため、**コード上の疑義**とする。

## 5. 座標系とCSS包含ブロック

### 5.1 座標の役割

- 描画座標: 保存される付箋位置、サイズ、接続点の論理位置
- 画面・ビューポート座標: DOMへ配置するときの位置
- 付箋ローカル座標: 操作領域ルートの左上を原点とする子要素位置

`position`は操作領域ではなく本体矩形の左上を表す。この意味を変更してはならない。

### 5.2 ボードルートの恒等transform

ボードルートには`transform: translate(0px, 0px)`がある。見た目を動かすためではなく、
`position: fixed`の子孫の包含ブロックをビューポートからボードルートへ切り替えるためである。
これにより配置物とメニューがボード埋め込み位置を基準にし、`overflow: hidden`でクリップされる。

これはCSSに埋もれていた重要な**復元仕様**である。恒等transformだけを「無意味」と判断して
削除してはならない。将来は、この意味を明示する専用の座標配置APIへ置き換えてもよい。

### 5.3 付箋ルートのtransformも包含ブロックを作る

`setViewportPositionByTransform()`は要素を`position: fixed; left: 0; top: 0`にし、
`transform: translate(...)`で配置する。したがって付箋ルート自身も、子孫のfixed要素に対する
新しい包含ブロックを作る。

矢印接続点は付箋ルートの子孫なので、DOMへ指定するtransformはビューポート絶対座標ではなく、
付箋ルートを基準にしたローカル座標でなければならない。

## 6. 矢印接続点

### 6.1 論理位置

接続点は本体矩形の各辺から15px外側に置く。30pxの操作余白内に収まり、操作領域の端より
内側に位置する。

```text
左右: centerX ± (width / 2 + 15px), centerY
上下: centerX, centerY ± (height / 2 + 15px)
```

各接続点の論理位置は描画座標で保持し、矢印の接続・接触判定・シリアライズに使う。
DOM表示用には操作領域左上を引いたローカル座標を別に算出する。

これは**復元仕様**である。

### 6.2 DOM表示

接続点の基準divは0×0で、内側に40×40のSVGを`translate(-50%, -50%)`して中心合わせする。
見える青丸は半径7px、青いstrokeは3pxだが、クリック可能範囲は40×40pxのSVG全体である。

基準divは`pointer-events: none`、SVGは`pointer-events: auto`である。クリックするとその接続点を
始点とする折れ線矢印を生成する。

### 6.3 表示状態

- 選択またはホバー中: 4接続点を表示する
- 選択解除またはホバー解除: 4接続点を非表示にする
- 全接続点表示モード: 薄緑の選択枠とともに表示する
- 表示・非表示は親のopacityと各接続点の`data-visibility="hidden"`を組み合わせている
- opacityの遷移時間は0.2秒

これは**復元仕様**である。

### 6.4 正常コミットに存在する危険な時間依存

接続点のコンストラクタは、最初に論理絶対位置を`setViewportPositionByTransform()`へ渡す。
しかし付箋ルートがtransform済みなので、この時点のDOM座標は包含ブロックに対して不適切である。

その後、textareaの遅延`onHeightChange`が発火すると、`update接続点座標()`が操作領域左上を
差し引いたローカル座標でtransformを上書きし、正常な位置になる。

つまり正常表示は、次の隠れた実行順序に依存している。

```text
付箋と接続点を未接続DOMとして構築
→ モデルへ追加
→ 配置物コンテナへDOM接続
→ setTimeout(0)でtextarea高さ確定
→ 接続点をローカル座標で上書き
```

この実行順序は現在の見た目を作る**実現機構**である。利用者から見た接続点の初期位置は保存するが、
同じ時間依存を新実装へ残す必要はない。新実装では接続点DOMを最初からローカル座標で構築し、
高さ通知の有無にかかわらず同じ初期位置を持たせる。

### 6.5 上下名称の疑義

正常コードは正のY方向を`上`、負のY方向を`下`として計算している。一方、ブラウザ座標は正のYが
画面下方向である。座標変換にもY反転は見当たらないため、名前と画面方向が逆転している可能性が
高い。接続方向のシリアライズにも影響するため、見た目だけを根拠に即時修正せず、実機で既存JSON
との対応を確認する。これは**コード上の疑義**であり、実際の画面方向と保存・復元結果を正とする。

## 7. ポインター操作とイベント境界

### 7.1 付箋ドラッグ

操作領域ルート全体がドラッグハンドルである。ポインター差分を拡縮率で割って描画座標へ加算し、
付箋本体、操作領域、接続点、接続済み矢印を同期して移動する。

選択中の複数配置物がある場合は、ドラッグした付箋自身を二重移動させず、残りの選択物を同じ差分で
移動する。

### 7.2 textareaはドラッグ領域から操作上分離する

textareaでは次のイベント伝搬を止める。

- `pointerdown`: 付箋ドラッグ開始と競合させず、テキストフォーカスを取得する
- `pointerup`: 親のドラッグ終了処理にフォーカスを奪わせない
- `click`: フォーカスを維持し、親のclick動作を発火させない
- `keydown`: Undo等のショートカットをCanvasへ伝えない

textareaのfocus時には付箋自体を選択状態へ移す。focus中だけ青い2px実線のoutlineをtextareaへ
表示し、blur時に消す。

これは操作品質に直結する**確定仕様**である。

### 7.3 付箋ディスペンサー

ボード起動時に描画座標(0,0)へ自由テキスト付箋を1枚生成する。その付箋のルートに一度限りの
click処理を登録し、利用された時点で同じ場所へ次の付箋を補充する。

textarea内のclickは伝搬停止されるため、文字編集だけでは補充を消費しない。これは
現在の動作として復元できるが、維持を前提にしない**再設計対象**である。ドラッグとclickの厳密な
成立条件も実機で記録する。

この方式では「付箋を作るためのUI」が、生成済みの実付箋そのものとして表現される。そのため
召喚器の段階から、通常付箋と同じ集約、textarea、選択、接続点、自動高さ計測、シリアライズ対象に
なり得るDOMを構築しなければならない。さらにボードのコンストラクタ内、document接続前に生成する
ため、DOM実測不能と初期化順序依存を直接引き起こしている。

### 7.4 付箋召喚UIの意味上の分離案

付箋召喚UIは「まだ配置物ではない生成コマンド」として扱い、実付箋から分離するのが第一候補である。

- 召喚UIは付箋に似た見た目を持ってよいが、配置物集約・接続点・textarea・シリアライズを持たない
- クリックまたはドラッグ開始時に初めて実付箋を生成する
- 生成した実付箋は通常の生成経路を1つだけ通る
- 召喚UIの補充はDOM複製ではなく、永続的なツール表示として扱う
- コンテキストメニューからの付箋生成も同じ生成コマンドへ合流させる

これにより「召喚UIの見た目」と「生成後の付箋の見た目」は同じデザイントークンを共有しながら、
DOMとドメイン上は別の意味を持てる。採用可否と具体的な操作は、実装前にユーザーと決定する。

### 7.5 現在の付箋生成経路

正常コミットには次の生成経路がある。

| 経路 | 生成位置 | Undo登録 | 特徴 |
|---|---|---|---|
| 付箋ディスペンサー | 描画座標(0,0) | なし | ボード構築中に実付箋を先行生成し、click後に補充 |
| キャンバスメニュー | 右クリック位置 | あり | 自由テキスト、タイトル付き、Fudaba札参照を選択 |
| AI続き生成 | 起点の右300px | あり | 新付箋と接続矢印を一括登録 |
| AI分解 | 対象の右300px、縦150pxから200px間隔 | あり | 複数付箋と接続矢印を一括登録 |
| クリップボード貼り付け | メニュー位置、位置なしなら画面中央 | あり | 平文は1付箋、グラフJSONは複数配置物 |
| テキストグラフ配置 | 指定起点から計算 | 呼出側で一括登録 | 希望IDを可能な場合だけ維持 |
| セーブデータ復元 | 保存済み位置 | 対象外 | 新規操作ではなくhydrate |

ディスペンサーだけが、通常の生成コマンドと異なるライフサイクルを持つ。

- ユーザー操作前からモデルの`配置物リスト`へ入る
- Undoコマンドへ登録されない
- 通常付箋なので選択、編集、接続、衝突判定、保存の対象になり得る
- ボードのDOM接続前にtextareaと接続点まで構築する
- セーブデータ読込時の`全配置物クリア()`では通常配置物と同様に除去される一方、
  `StickyGraphBoard._一番上の付箋`はその旧インスタンスを参照し続ける可能性がある

これは見た目の問題ではなく、「生成ツール」と「生成済みドメインオブジェクト」を同一視した
製品仕様・モデル境界の問題である。特殊なCSSと初期化順序は、この境界不在を成立させるための
下流の補償になっている。

## 8. 表示状態と重なり順

- 通常配置物のz-indexは0
- 選択中配置物のz-indexは100
- 付箋内部ではコンテンツ1、ヘッダー2、左右リサイズハンドル3
- コンテキストメニューは配置物コンテナより上
- 選択解除時は通常z-indexへ戻す

選択した付箋を他の配置物より前面へ出し、リサイズハンドルをテキストより手前に保つことが
利用者向けの**復元仕様**である。数値自体は実装詳細として一元管理する。

## 9. コンテンツ種別ごとのサイズ契約

### 9.1 自由テキスト

- 新規サイズ: 200×52px

## 10. 静的解析だけでは画面結果を確定できない箇所

次はコード上に複数の値や時間順序が存在する。正常コミットを実行して最終的な外観・操作結果を
計測し、その結果を保存対象として確定する。コードだけを見て一方を不要と判断してはならない。

1. ロード復元時の`minHeight`だけ50pxで、新規自由テキストの52pxと一致しない
2. タイトル付きの生成時高さ70pxと、空欄2つの通知後高さ100pxが一致しない
3. 接続点の初期表示座標がtextareaの遅延高さ通知による上書きに依存する
4. `上`と`下`のY方向がブラウザ座標の名称と逆に見える
5. 左右リサイズに最小幅がない
6. 初期状態は親opacityが0でもSVGのpointer-eventsが有効であり、属性による完全非表示が最初から
   適用される保証がない
7. 高さ変更時に接続点更新が直接呼び出しと`onResize()`内で重複する

これらの実現機構を同じ形で残す必要はないが、現在の画面に現れている結果はすべて仕様として残す。

## 11. 新実装が満たすべき受け入れ条件

1. 空の自由テキスト付箋は黄色面とtextareaがともに200×52pxである
2. 黄色面の周囲30pxは透明だが、ドラッグ・選択・リサイズに使える
3. 選択枠は黄色面ではなく、左右ハンドルを含む操作領域全体を囲む
4. 左右ハンドルは操作領域の外周にあり、黄色面との間に透明余白がある
5. 4接続点は本体各辺から15px外側、操作領域内に表示される
6. 接続点は初回描画から正しい位置にあり、textareaの遅延高さ通知を待たない
7. 付箋の移動、左右リサイズ、テキストによる高さ変更、パン、ズームのすべてで接続点と矢印が追従する
8. textarea操作は付箋ドラッグやCanvasショートカットを誤発火させない
9. document未接続時のDOM実測値で空付箋の高さを決めない
10. ボードをタブ内へ埋め込んでも、配置物とメニューはボードルートを基準に配置・クリップされる
11. 背景色変更は本体矩形だけに反映され、透明な操作領域を塗らない
12. セーブ・ロード後も本体矩形の位置とサイズが一致する

## 12. リファクタリング方針

新実装では、CSSに意味を密輸せず、次の概念をTypeScript上で明示する。

- `付箋本体矩形`
- `付箋操作領域矩形`
- `矢印接続点配置`
- `付箋表示状態`
- `付箋操作状態`
- `付箋生成コマンド`
- `付箋召喚UI`

CSSは各概念の描画を担当するが、どの矩形が選択・衝突・ドラッグ・背景・接続点の基準になるかは
TypeScript側の名前と型で読めるようにする。

最初の実装対象は「接続点を最初から付箋ローカル座標で構築し、非同期高さ通知への依存を除く」こと。
ただし、付箋ディスペンサーを残したままこの問題だけを直すと、document接続前に実付箋を構築する
特殊経路が残る。先に召喚UIを実付箋から分離するか、少なくとも通常付箋と召喚用付箋の生成経路を
明示的に分ける。その後、本体要素の導入、接続点配置、操作配線の分割を受け入れ条件ごとに進める。

## 13. 過去に同等と判断され、実機では却下された変更

コミット`11720b7`では、外枠の明示的な高さ指定をやめ、CSSの通常フローによるauto高さへ
委ねる変更が行われた。同時にテキストの改行数から初期高さを同期計算し、接続点を構築後に
追従させる方式へ変更された。

コード上は「コンテンツの実高さと外枠を常に一致させる」改善に見えたが、ユーザー実機確認で
「全然ダメ」と判定され、コミット`fcd3fbe`で付箋1行化関連変更ごと差し戻された。

この履歴から、次を仕様復元上の原則とする。

- `height: auto`と明示的な外枠高さは、付箋全体の見た目・操作について同等とはみなさない
- 数式上の本体サイズが一致するだけでは不十分で、透明余白、選択枠、ハンドル、背景、初期描画、
  接続点まで同時に比較する
- 「より自然なCSS」という理由だけで正常コミットの配置規則を置き換えない
- 置き換えは、受け入れ条件を状態別に実機比較した後にのみ完了とする

30pxの操作余白と15pxの接続点余白は初回コミット`7c7aafc`から存在し、衝突判定、背景、選択枠、
接続点相対座標の全経路で一貫して使われている。後付けの装飾ではなく、付箋操作の初期設計から
存在する中心的な寸法である。

## 14. 2026-07-16実装結果: 召喚UIの分離

`付箋召喚UI`を新設し、左上の付箋置き場を配置物モデルから分離した。

```text
付箋召喚操作領域（透明、260×112）
└─ 付箋召喚本体（実背景、200×52以上）
   └─ 下書きtextarea（rows=1）
```

- 召喚UIは`I配置物集約`ではなく、保存・選択・接続点・衝突判定の対象外
- ドラッグ開始時に`CanvasView.自由テキスト付箋を生成する()`を呼び、初めて実付箋を生成
- キャンバスメニューからの自由テキスト生成も同じメソッドへ合流
- 召喚UIへ入力した下書きは生成した付箋へ渡し、召喚UI自身は空・52pxへ戻す
- 操作領域の透明余白30px、本体200×52px、placeholder、文字組みは従来表示を維持
- 旧`付箋をめくる動作`と`StickyGraphBoard._一番上の付箋`を削除

召喚UIのDOMではcontent-boxグラデーションを使わず、透明な操作領域と実背景を持つ本体要素を
分離した。見た目は維持しながら、DOMから各領域の意味を読み取れる構造になった。

### 14.1 textareaのHTML既定値による2行化

実行時調査で、`TextAreaC`へ`rows`を指定していない場合、HTMLの既定値`rows=2`が適用されることを
確認した。空文字は既知の52pxへ固定されるが、1文字入力して`height:auto`へ戻した瞬間、
`scrollHeight`が2行分の72pxになっていた。

実付箋と召喚UIのtextareaへ`rows: 1`を明示した。これにより上下padding 16pxずつとlineHeight
20pxの合計52pxが、空文字だけでなく1行の非空文字でも維持される。

### 14.2 実行時確認値

| 状態 | 確認結果 |
|---|---|
| ボード起動直後 | 召喚UIのtextareaだけが1個。実付箋は0個 |
| 召喚操作領域 | 260×112px、透明 |
| 召喚本体・textarea | 200×52px、背景`rgb(255,255,208)` |
| 召喚UIへ1行入力 | 52pxを維持 |
| ドラッグ後 | 召喚UIは元位置に残り、下書きを持つ実付箋が1枚生成 |
| 実付箋へ1行入力 | 200×52px、`rows=1` |
| 接続点 | 本体左右辺から15px外、上下辺から15px外 |
| Undo | 生成した実付箋だけが消え、召喚UIは残る |

検証は本番ビルドしたElectronをremote debugging付きで起動し、DOM矩形と値を直接取得して行った。

### 14.3 新規生成と再読込で初期寸法を共有

従来の`CanvasItemFactory`では、新規生成時の最小高さと保存データ再読込時の最小高さが別々に
数値指定され、再読込だけ`50px`になる経路が残っていた。これは同じ付箋コンテンツが生成経路で
異なる表示仕様を持つ状態である。

`付箋初期寸法.ts`へ自由テキスト、タイトル付き、札参照の初期サイズと最小高さを集約した。
新規生成と再読込の双方がコンテンツ種別から同じ値を取得するため、自由テキスト付箋はどちらの
経路でも最小52pxとなる。

### 14.4 ドラッグ操作領域を本体の兄弟要素へ分離

緑枠と赤枠は装飾ではなく、利用者へドラッグ可能範囲を伝える表示仕様である。一方、黄色い付箋本体は
常時テキスト入力可能にするため、意図的にドラッグ不可とする。

この二つをDOMの重なり順とイベント伝搬で両立させず、次の兄弟構造で表現する。

```text
付箋座標シェル（位置と全体寸法だけを持つ）
├─ 付箋ドラッグ操作領域（本体と重ならない）
│  ├─ 上ハンドル（30px）
│  ├─ 右ハンドル（30px）
│  ├─ 下ハンドル（30px）
│  └─ 左ハンドル（30px）
└─ 付箋本体（黄色、textareaを含む）
```

操作領域の親は`pointer-events: none`、上下左右のハンドルだけを`pointer-events: auto`とする。
イベントは4本から共通の操作領域へバブルするため、`PointerWife`は一つでよい。中央にはドラッグ用DOMが
存在しないので、textareaがイベントを止める順序やz-indexにドラッグ可否が依存しない。

枠線の責務は次の通り。緑枠は「ポインタ直下の素片がドラッグ可能」を示すヒットテスト表示ではない。
現在操作対象として認識されている付箋と、その外周にドラッグ可能な領域があることを、付箋全体の境界で示す。

| 状態 | 枠線 | 意味 |
|---|---|---|
| 未選択の付箋内をホバー | 緑の破線 | この付箋の外周にドラッグ可能領域がある |
| 付箋を選択 | 赤の破線 | 選択中で、外周から移動できる |
| 矢印選択 | 薄緑の破線 | 接続操作の対象 |

ポインタが黄色本体、外周ハンドル、接続点のいずれにあっても、付箋の境界内なので緑枠を表示する。
同一付箋内の子要素間を移動してもホバー対象を設定し直さない。これにより接続点周辺での緑枠の点滅を防ぐ。
緑枠は別の付箋または召喚UIがホバー対象になるか、キャンバス操作でホバー状態を解除するまで維持する。
ドラッグの実ヒットテストは上下左右の4ハンドルだけが担い、黄色本体は緑枠表示中でもドラッグ不可・直接編集可のままとする。

同じ`付箋ドラッグ操作領域`を実付箋と召喚UIで共有する。30pxの操作余白と3種類の枠線は
`付箋操作仕様.ts`へ集約し、両者とCSSが同じ定義を参照する。

実行時には次を確認した。

- 召喚UI・実付箋とも外周260×112px、本体200×52px
- 外周、黄色い本体、接続点のいずれをホバーしても緑枠を維持
- 同一付箋内の子要素間移動で緑枠を点滅させない
- 召喚ドラッグ後の実付箋は赤枠
- 黄色い本体から100px相当のドラッグ操作をしても位置は不変で、textareaがフォーカスされる
- 外周から同じ操作をすると付箋が100px移動する
