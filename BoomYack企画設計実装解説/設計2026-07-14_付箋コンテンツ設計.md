# 設計2026-07-14: 付箋コンテンツ設計(札#34 根本設計検討)

## 0. 経緯

札#34「Boomyackの付箋のデザインを増やしたい」に対し、2026-07-14の先行調査で「View2(ヘッダー帯プロトタイプ)の配線復活」を最も安く着手できる案として提示したが、ユーザーに却下された。

> その付箋は失敗作。構造が微妙だった。もっと根本的に用途とか考えてほしい。

表面的な見た目の追加ではなく、**BoomYackの付箋が何のために使われるか**から出発して構造を決め直す。本文書はその根本検討の記録である。

## 1. 用途分解

BoomYackボード上で人間とAIが付箋を使って行う作業を洗い出し、各用途が付箋の中身に要求する形を導出する。

| 用途 | やること | 付箋の中身に求められる形 | 現行での可否 |
|---|---|---|---|
| 思考整理・ブレスト | 思いついたことを書き殴り、矢印でつなぐ | 自由テキスト(1個の文字列) | 可(現行そのもの) |
| アイデア出しの深掘り | AI分解(LLM分解/区切り分解)で1枚を複数枚に割る、AI生成で続きを作る | 自由テキスト。AI入出力は常に平文が前提 | 可 |
| 議事録・決定事項の記録 | 「何を決めたか」を一目で識別しつつ詳細を読む | タイトル(見出し)+本文の分離。タイトルだけでボード俯瞰時に識別したい | 不可(見出しと本文が同じテキスト欄に同居し、俯瞰時にタイトルだけを目立たせられない) |
| 用語集・データ定義 | 概念とその説明、パラメータ名と値を並べる | キー: 値 の対応リスト表示 | 部分的(改行区切りテキストで代用可能だが、見た目上の整形・強調はできない) |
| WBS(作業分解構造) | タスクを付箋として空間配置し、依存を矢印で表す(Jimbo ARCHITECTURE.mdのPhase D構想と一致) | 状態(未着手/進行中/完了等)が色や記号で一目瞭然、担当者が見える、詳細はクリックで別ビューに飛べる | 不可(状態・担当は付箋データに存在しない概念。テキストに書き込む運用では状態変化が手作業になり実態と乖離する) |
| 開発管理ボードとの連携(Phase D) | Fudaba札(作業アイテム)の現在状態をボード上でリアルタイムに見る | 外部ストアを参照する投影。データの実体は付箋ではなく外部にあり、付箋は表示窓 | 不可(現行の付箋データはテキストを保持する実体そのものであり、外部参照という概念がない) |
| ラベルによる分類整理 | 案件・カテゴリごとに色分けして俯瞰する | 背景色・文字色 | 可(既存の`付箋設定状態`で対応済み) |

導出される中身の形は次の5種に整理できる。

1. **自由テキスト**(現行) — 単一の文字列
2. **タイトル付き自由テキスト** — 見出し+本文の2フィールド
3. **キー値リスト** — 複数の「キー: 値」ペア
4. **チェックリスト** — 複数行 + 各行の完了フラグ
5. **外部参照の投影** — 付箋自身はデータを持たず、外部ID(Fudaba札ID等)を保持して表示時に参照解決する

このうち4(チェックリスト)は今回のヒアリング(WBS用途)からは3(キー値リスト、状態を1キーとして表現可能)に吸収できるため独立種別にはしない。5(外部参照)はPhase D領域であり本設計では「型の置き場所を用意する」に留め、実装はPhase D側に委ねる(理由は3章で述べる)。

## 2. 現行構造の限界分析

### 2.1 データ層: `付箋データ`はtextを1本しか持てない

`基本オブジェクト/描画キャンバス/データクラス.ts`の`付箋データ`は次の形である。

```
付箋データ { id, position, size, text: string, 設定状態: 付箋設定状態 }
```

`text`は単一文字列。タイトルと本文を分けたい、キー値ペアを持ちたい、という要求はこの型に居場所がない。かといって`text`に`"# タイトル\n本文"`のような記法を密輸すると、AI連携仕様(`AI連携仕様.md`)が定義する`/BoomYack/AI/Generate`・`/BoomYack/AI/Decompose`は平文の`text`をそのままLLMに渡す設計であり、密輸した記法がLLM出力に紛れ込んで壊れる。プリミティブへの意味の密輸は避けるべきというコーディング憲法の原則がそのままここに当てはまる。

### 2.2 集約層: `付箋集約`は既に2つのView型のunionを抱えている

`基本オブジェクト/配置物/付箋2/付箋集約.ts`:

```
public readonly view: 自動リサイズ付箋View<座標点T> | 自動リサイズ付箋View2<座標点T>;
```

コンストラクタでは常に`自動リサイズ付箋View`を生成しており(`自動リサイズ付箋View2`の行はコメントアウト済み)、実質未使用のunion枝が型定義として残っている。これは「付箋の見た目違いをView丸ごとの別クラスとして増やす」やり方の代償が既に表面化している証拠でもある。

### 2.3 View2はなぜ失敗作になったか(実コード検証)

`付箋2/自動リサイズ付箋View.ts`(現行稼働、493行)と`付箋2/自動リサイズ付箋View2.ts`(未配線プロトタイプ、418行)を比較した結果、以下が判明した。

- **View2はView本体の複製として作られている。** ドラッグ処理・リサイズハンドル処理・矢印接続点計算(`calculate矢印接続ポイント`等)・選択状態のアウトライン切替・zIndex制御・`付箋ボードTransform`計算は、ほぼ同一のコードがView/View2の両方に存在する(1行1行はほぼ一致し、差分はヘッダー分のオフセット計算のみ)。ヘッダー帯という**表示上の差分**を足すために、ドラッグ・矢印接続・選択状態という**振る舞いレベルの重い責務**まで丸ごとコピーされている。
- **View2はViewの機能追加に追従していない。** 現行View(493行)には、View2作成後に追加されたと見られる以下の機能が存在するが、View2(418行)には存在しない。
  - 多段格子コンテキストメニュー(保存/削除/AI分解/AI生成/グラフ操作/マイク入力トグルなど、`グラフ操作マニュアル.md`が説明する全機能)の配線
  - `onTextCommit`によるUndo/Redoコマンド連携(`配置物テキスト変更コマンド`)
  - `onFocus`時に自身を選択状態にするフォーカスバグ対策
  - マイク入力状態の監視・アイコン切り替え
  
  つまりView2へ切り替えると、ヘッダー帯と引き換えに右クリックメニュー・Undo・マイク連携が丸ごと退行する。ユーザーが「失敗作」と評した実体はここにある。
- **「枠」と「中身」が同一クラスに同居しているのが根本原因。** ドラッグ・リサイズ・矢印接続点・選択状態・コンテキストメニュー・zIndexは付箋の見た目(自由テキストかヘッダー付きか等)に関わらず共通の「枠」の責務である。View/View2はこの枠の責務ごと丸ごと1クラスに閉じ込めており、中身(テキストエリアのみ、またはヘッダー+テキストエリア)を変えたいだけなのに枠を複製するしかない構造になっている。

### 2.4 生成層: `CanvasItemFactory`も同型の重複を持つ

`create付箋`(新規生成)と`create付箋FromData`(ロード時復元)は、コンテキストメニュー依存関係の組み立てを含め65行前後がほぼ丸ごと重複している(差分は`position`/`text`の初期値算出のみ)。付箋の種類が増えるたびに、この重複がさらに枝分かれする懸念がある。新設計では生成ロジックの共通化も併せて検討対象に含める。

| 観点 | 案A: 既存の複製拡張(View2型を種類ごとに増やす) | 案B: 枠とコンテンツの分離 | 案C: 種類ごとに独立した`I配置物集約`実装を増やす |
|---|---|---|---|
| 内容 | 種類ごとに`自動リサイズ付箋View3, View4...`を丸ごと複製して作る | `付箋集約`/`付箋View`は「枠」(ドラッグ・リサイズ・矢印接続・選択・コンテキストメニュー・zIndex)の責務のみに専念し、中身は`I付箋コンテンツView`として差し替え可能なプラグインにする | 「付箋」概念とは別に`Fudaba札付箋集約`のような新しい`配置物type`を増やし、`I配置物集約`を個別実装する |

| 既存データ互換 | `text`のみのJSONは新種別のデフォルトとして読めるが、種類ごとに別JSONスキーマが必要になり分岐が増える | `付箋データ`に中身種別の判別共用体を足すだけで済み、`type: "付箋"`という配置物type自体は変えない。既存の`text`のみJSONは「自由テキスト種別」として変換すればよい | 新`配置物type`の追加が必要。既存の折れ線矢印との接続点解決・衝突判定・シリアライズの分岐(`CanvasItemFactory.createItemFromData`のswitch等)に新caseを足す必要があり影響範囲が広い |
| 実装規模 | 中〜大(種類が増えるたび線形に増加。かつ機能退行の手戻りリスクを常に抱える) | 中(最初に枠/中身の分離という1回のリファクタが必要だが、以降の追加は小さい) | 大(構造的には可能だが、既存の「付箋」という概念と本質的に地続きの表示差分に対して、配置物type自体を割るのはオーバースペック) |
| SengenUI/100行規約適合 | View本体が493行など既に規約超過であり、複製すればするほど規約違反が増える | 枠(ドラッグ・矢印接続・コンテキストメニュー)とコンテンツ(自由テキスト/タイトル付き/キー値)をそれぞれ責務単位のファイルに分割でき、100行規約に寄せやすい | 型ごとに新しい集約・View・VM一式が必要になり、ファイル数は増えるが個々の行数は制御しやすい。ただし枠機能の重複は避けられない |

### 推奨: 案B(枠とコンテンツの分離)

用途カタログの1〜4(自由テキスト・タイトル付き・キー値リスト・チェックリストは3に統合)は、いずれも「付箋という概念の中の表示バリエーション」であり、ドラッグ・矢印接続・選択・コンテキストメニューという枠の振る舞いは変わらない。変わるのは中身の描画とシリアライズ形式だけである。この性質は「モード拡張で十分」という2026-07-14先行調査の判断材料と整合するが、そのモード拡張の実装方法が「View全体の複製」であってはならない、というのが今回の教訓である。案Bはその教訓を構造に反映したものであり、2.3で特定した失敗原因(枠と中身の癒着)をそのまま解消する。

用途カタログの5(外部参照の投影、Fudaba札参照)は、データの出自が外部ワークスペースストアであり「テキストを保持する付箋」と本質が異なるため、案Cの「新しい配置物type」が妥当という判断は先行調査から変わらない。ただし実装はJimbo ARCHITECTURE.mdが定めるPhase D(BoomYackビュー統合)のスコープであり、Fudaba API連携設計が先に必要なため本設計では対象外とする。案Bで整備する`I付箋コンテンツView`契約と`付箋データ`の判別共用体化は、将来Phase Dで「外部参照コンテンツ」を追加する際の受け皿にもなる(コンテンツ種別を1つ足すだけで済む)。

## 4. 推奨案の詳細設計

### 4.1 責務の再配置

現行の`自動リサイズ付箋View`(493行)を以下に分離する。

- **枠(継続してこのクラスが持つ)**: ドラッグ・リサイズハンドル・矢印接続点計算・選択状態のアウトライン・zIndex・コンテキストメニューの配線・`付箋ボードTransform`計算
- **中身(新設する`I付箋コンテンツView`実装へ切り出す)**: テキストエリアの描画、将来のヘッダー帯・キー値リスト表示等

### 4.2 `I付箋コンテンツView`契約(案)

```
interface I付箋コンテンツView extends LV2HtmlComponentBase {
    /** AI生成/分解・グラフのテキストコピー等が要求する平文表現 */
    get text(): string;
    setText(text: string): void;
    /** 高さ変化を枠へ伝える(自動リサイズのため) */
    onHeightChange(callback: (newHeight: number) => void): void;
    設定を適用(設定: 付箋設定状態): void;
}
```

すべてのコンテンツ型が`text`の平文射影を持つ制約は、2.1で述べたAI連携仕様(`/BoomYack/AI/Generate`・`/BoomYack/AI/Decompose`)およびグラフのテキストコピー機能が平文前提である以上、外せない。タイトル付き種別なら「タイトル+本文」、キー値リストなら「キー: 値」を改行結合した文字列を`text`として返す。

### 4.3 `付箋データ`の中身種別を判別共用体化

```
type 付箋コンテンツデータ =
    | { 種別: "自由テキスト"; text: string }
    | { 種別: "タイトル付き"; タイトル: string; 本文: string }
    | { 種別: "キー値リスト"; 項目リスト: ReadonlyArray<{ キー: string; 値: string }> }
```

`付箋データ`は`text: string`単独から`コンテンツ: 付箋コンテンツデータ`を持つ形へ拡張する。後方互換は「版ごとの型+最新への変換」の原則に従う。

- 旧JSON(`text`のみ、`種別`キーなし)を読んだときは`{ 種別: "自由テキスト", text: json.text }`として`fromJSON`内で変換する
- 最新の`付箋データ`型自体は互換ハックを持たず、`I付箋JSON`のパース時点で1回だけ変換する

### 4.4 生成層の重複解消

`CanvasItemFactory.create付箋`と`create付箋FromData`の共通部分(コンテキストメニュー依存関係の組み立てなど)を private ヘルパーに抽出し、`position`/`コンテンツ`の初期値算出だけを呼び出し側で分岐させる。コンテンツ種別が増えても生成ロジックの重複が線形に増えない構造にする。

## 5. 段階実装計画(依存順、実装はこの設計文書のコミット後にユーザー方針確認を経てから着手する)

1. **枠とコンテンツの分離リファクタ(振る舞い変更なし)**: 現行`自動リサイズ付箋View`(493行)から、テキストエリア描画部分を`自由テキストコンテンツView`(`I付箋コンテンツView`実装)として切り出す。ドラッグ・矢印接続・コンテキストメニュー等の枠側の挙動は一切変えず、既存の自由テキスト付箋が今まで通り動くことをグラフ操作マニュアル記載の全操作(AI分解・AI生成・コピー・JSON出力・Undo/Redo・コンテキストメニュー)で確認する。未配線の`自動リサイズ付箋View2.ts`はこの時点でアーカイブ(削除または`99_Archive`相当への退避)し、二重メンテナンス対象から外す
2. **`付箋データ`の判別共用体化+後方互換変換**: 4.3の型を導入し、既存セーブデータ(`text`のみ)が引き続き読み込めることをロードテストで確認する。この時点ではUIからコンテンツ種別を切り替える手段はまだ提供しない(自由テキスト種別のみ生成される)
3. **2種類目のコンテンツ(タイトル付き自由テキスト)を追加**: `タイトル付きコンテンツView`を実装し、付箋コンテキストメニューに「コンテンツ種別を変更」等の導線を追加する。ここで初めて2.3で失敗したヘッダー帯の見た目を、枠を複製せずに再現できることを検証する
4. **3種類目(キー値リスト)を用途が具体化した時点で追加**: 現時点では優先度を確定しない。WBS用途で実際に必要になったタイミングで着手する
5. **外部参照コンテンツ(Fudaba札参照)はPhase D着手時に着手**: Jimbo ARCHITECTURE.mdの段階計画通り、Fudaba API連携設計(データ層の参照解決・状態のリアルタイム反映方式)が先に必要なため、本札(#34)のスコープには含めない

最初の一歩(1)は既存の見た目・挙動を一切変えないリファクタであり、最もリスクが小さい。ここで枠/コンテンツの境界が実際に機能することを検証してから、2以降で新しい中身の形を積み増す。

## 6. 参考: 本検討で確認した既存コードの事実関係

- `基本オブジェクト/配置物/付箋/`配下の`自動リサイズ付箋View.ts`(286行、旧世代)は、スタイル定義とテキストエリアコンポーネントのみ兄弟ファイルとして再利用されており、クラス自体はどこからもインスタンス化されていない(実質デッドコード)
- `付箋集約.vm`(`I付箋VM`型)はマーカーインターフェース(空)であり、コンストラクタ内で値が代入されていない。VM層は現状の付箋実装では実質使われていない
- `I配置物.ts`の`配置物type`には`"なめらか曲線矢印"`が型として予約済みだが実装は0件(矢印の滑らかモードは本設計のスコープ外、別途検討が必要)
